# J01 — First Jenkins Pipeline

## 1. Pipeline Name
`J01-first-jenkins-pipeline` (Declarative Jenkins Pipeline)

## 2. Objective
Design, implement, execute, and troubleshoot a foundational 4-stage Declarative Jenkins Pipeline (`Checkout`, `Build`, `Test`, `Finish`) running on a containerized Jenkins LTS controller.

## 3. Problem Being Solved
Traditional Jenkins Freestyle jobs rely on manual UI clicks, making build configurations difficult to version-control, audit, review, or reproduce after server failures.

Defining CI/CD workflows as code using Declarative Pipeline solves this by providing a structured, syntax-validated, and reproducible build skeleton.

## 4. Technologies Used
- **Jenkins LTS:** `jenkins/jenkins:lts` Docker image
- **Docker:** Container runtime with persistent named volume `jenkins_home`
- **WSL2:** Ubuntu on Windows 11
- **Groovy:** Jenkins Declarative Pipeline DSL

## 5. Architecture

```text
Manual Trigger
      |
      v
Jenkins Controller (Docker)
      |
      v
Agent Allocation (agent any)
      |
      v
Workspace Provisioning
      |
      v
Stage 1: Checkout
      |
      v
Stage 2: Build
      |
      v
Stage 3: Test
      |
      v
Stage 4: Finish
      |
      v
Console Output & Build Status
(SUCCESS / FAILURE)
```

- **Jenkins Controller:** Validates the Declarative syntax before execution and orchestrates stage progression.
- **Agent (`agent any`):** Allocates an available executor (built-in controller node) and provisions an isolated job workspace.
- **Sequential Execution:** Stages execute strictly in order. Any non-zero exit code halts the pipeline immediately and skips downstream stages.

## 6. Prerequisites

- Docker Engine accessible from WSL2 Ubuntu.
- Jenkins LTS container running with persistent volume `jenkins_home`.
- Ports `8080` (Web UI) and `50000` (agent communication).
- Suggested Jenkins plugins installed, specifically the **Pipeline** plugin.

## 7. Implementation Explanation

The pipeline uses the five core Declarative blocks:

- `pipeline`
- `agent`
- `stages`
- `stage`
- `steps`

### Jenkinsfile

```groovy
pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps {
                echo 'Checkout Started!'
                sh 'pwd'
            }
        }

        stage('Build') {
            steps {
                echo 'Building...'
            }
        }

        stage('Test') {
            steps {
                echo 'Testing...'
            }
        }

        stage('Finish') {
            steps {
                echo 'Finished'
            }
        }
    }
}
```

### Explanation

- `echo` prints log messages directly through Jenkins without spawning a subshell.
- `sh 'pwd'` executes a Linux shell command inside the container to verify the active workspace path.

## 10. Failure Scenarios and Troubleshooting

### Scenario 1: Bare Shell Command in Groovy (`MissingPropertyException`)

**Cause:**

Writing `pwd` directly inside `steps` instead of `sh 'pwd'`.

Jenkins parses the script as Groovy, so `pwd` is interpreted as an undefined variable.

**Fix:**

Wrap OS commands inside the `sh` step.

```groovy
sh 'pwd'
```

### Scenario 2: Intentional Stage Failure (`sh 'exit 1'`)

**Cause:**

Added `sh 'exit 1'` inside the `Test` stage in Build #2.

**Observed Behavior:**

- Jenkins logged `ERROR: script returned exit code 1`.
- Marked the `Test` stage as failed.
- Skipped the `Finish` stage completely.
- Ended with `Finished: FAILURE`.

**Production Takeaway:**

Cleanup tasks and failure notifications must never rely on a standard final stage.

They belong in a `post` block:

```groovy
post {
    always {
        echo 'Pipeline execution completed.'
    }

    failure {
        echo 'Pipeline failed.'
    }
}
```

**Resolution:**

Removed `sh 'exit 1'` and executed Build #3 to restore `Finished: SUCCESS`.

## 11. Important Concepts Learned

1. Declarative Pipeline structure and upfront syntax validation.
2. Difference between built-in Jenkins steps (`echo`) and shell execution (`sh`).
3. Workspace isolation inside `/var/jenkins_home/workspace/<job-name>`.
4. Fail-fast execution driven by Linux exit codes (`0` = pass, non-zero = fail).
5. Persistent Jenkins state using Docker named volumes (`jenkins_home`).

## 12. Interview Questions and Answers

**Q1: Why do teams prefer Declarative Pipelines over Freestyle jobs?**

Declarative Pipelines store CI/CD logic as code (`Jenkinsfile`), enabling Git version control, pull request reviews, auditability, and instant disaster recovery—none of which are natively available in UI-configured Freestyle jobs.

**Q2: What happens in a Jenkins Pipeline when a shell command exits with a non-zero status code?**

Jenkins immediately halts execution of the current stage, skips all subsequent stages, and marks the build as `FAILURE`. Only applicable `post` conditions (such as `always` or `failure`) will still run.

**Q3: Why mount a Docker named volume to `/var/jenkins_home`?**

Container filesystems are ephemeral. Mounting a named volume ensures jobs, build history, plugins, and encrypted credentials persist across container restarts, recreations, and image upgrades.
